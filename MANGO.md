# Mango

One file: what this is, why it is built this way, what exists today, what is left.
Phase detail and acceptance criteria live in [plan.md](plan.md); this is the map.

---

## 1. What Mango is

An incident management platform that investigates its own incidents with a multi-agent
AI workflow reading the failing application's real logs.

The loop: an application breaks → an incident exists in Mango → five agents run over the
logs around that incident → an engineer reads a report naming a probable cause, the
evidence behind it, a confidence level, and what to check next.

A companion app, `dummycommerce/`, is a deliberately breakable storefront. It fails on
demand, writes JSONL logs, and files incidents against Mango. It is the test subject that
makes the whole thing demonstrable without a real outage.

## 2. Why it is built this way

**The investigation is evidence-bound, not a chatbot.** Log retrieval is ordinary tested
Python (`app/services/evidence.py`), not a model with filesystem access. The model only
ever sees a bounded, credential-scrubbed set of records. This is the one property a
generic "paste your error into an LLM" tool cannot truthfully claim.

**Every agent run is persisted.** `AgentExecution` stores each agent's output, duration
and reasoning, so any conclusion traces back to what produced it. An unauditable diagnosis
is worthless at 3am.

**The report separates facts from conclusions** and lists evidence that is missing or
contradicting. Confidence tracks evidence quality, demonstrably: the same agents report
`low` on a single log line and `medium` on a correlated failure sequence.

**Layered: router → service → repository.** Routers do HTTP, services do rules,
repositories do SQL. The graph nodes call services, never the database.

**No build step on the frontend.** The console is one static HTML file with vanilla JS,
served by FastAPI at `/console`.

**A four-layer budget guard around the LLM**, because the project runs on a free tier:
shared Redis RPM pacing → an atomic PostgreSQL daily request budget → a durable Celery queue →
a provider-driven 429 cooldown. The free tier is roughly 20 requests per day per model, and
aliases silently move between models, so the model is pinned, not aliased.

## 3. What exists today

**Stack:** FastAPI, SQLAlchemy 2, PostgreSQL, Redis, Celery, Alembic, Pydantic v2, PyJWT,
pwdlib/argon2, LangGraph, LangChain, Gemini, optional OpenRouter, OpenTelemetry, Prometheus.
Jaeger, GitHub Actions CI.

**Tables (12):** `users`, `incidents`, `comments`, `activity`, `workflow_runs`,
`agent_executions`, `service_keys`, `log_records`, `detection_rules`, `incident_groups`,
`daily_llm_budgets`, `escalation_policies`.

**API (28 endpoints):**

- `POST /auth/register`, `POST /auth/login`, `GET /auth/me`
- `PATCH /auth/users/{id}/role` (admin only)
- `POST /incidents`, `GET /incidents`, `GET /incidents/{id}`,
  `PATCH /incidents/{id}`, `PATCH /incidents/{id}/status`,
  `PATCH /incidents/{id}/assign`, `POST /incidents/{id}/acknowledge`,
  `GET /incidents/{id}/activity`
- `POST /incidents/{id}/comments`, `GET /incidents/{id}/comments`,
  `PATCH /comments/{id}`, `DELETE /comments/{id}`
- `POST /incidents/{id}/investigate`, `GET /incidents/{id}/investigation`,
  `GET /incidents/{id}/investigation/stream` (SSE),
  `GET /incidents/{id}/investigations`, `GET /investigations/{run_id}`,
  `GET /investigations/quota`
- `POST /ingest/logs` (scoped service key; JSONL or gzip; batches up to 500 records),
  `GET /console`
- `GET|POST /escalation-policies`, `PATCH /escalation-policies/{id}` (admin only)

**Log ingestion and detection:** services send bounded JSONL batches with a per-service
ingest key. Mango stores only a SHA-256 key hash, scrubs credential-like context fields,
and writes records to indexed PostgreSQL storage. Detection rules open incidents when a
service crosses error-count, critical-pattern, or error-rate thresholds. Open incidents are
deduplicated by a normalized failure fingerprint; repeated matches update occurrence counts,
and incidents across services can share a group through a common request ID or upstream.
Investigation evidence is retrieved from a bounded database query; the model still receives
only the scrubbed record set. The deterministic 10k outage fixture is generated by
`python -m scripts.generate_outage_fixture`; `python -m scripts.replay --fixture
load/outage.jsonl --report` measures collapse. The live replay passed against PostgreSQL:
400 failures became 6 incidents (66.7:1). The command waits for ingestion and detection
completion and tags each run to keep measurements isolated. `load/ingest.js` measures the
500-record request path; its live p95 measurement remains pending because k6 is not installed.

**The agent pipeline**, a LangGraph `StateGraph`, always in this order:
`planner` → `evidence_collector` → `root_cause` → `fix_recommendation` → `report`.
Two of them (`evidence_collector`, `report`) are plain Python with no model call.
Structured output uses LangChain's `with_structured_output(schema, include_raw=True)`.
Each node retries transient failures up to twice. Completed node outputs are persisted and a
redelivered task resumes at the first unfinished node. Celery workers consume Redis tasks;
the daily provider budget is an atomic PostgreSQL upsert, and a shared Redis slot paces model
calls across workers. The console receives completed node outputs and reasoning over SSE.

**Rules implemented:** severity `LOW|MEDIUM|HIGH|CRITICAL`; status `OPEN` →
`INVESTIGATING` → `RESOLVED`, one way, no skipping. Permissions are per incident, not
role based: only the creator assigns, only creator or assignee changes status, only the
author edits or deletes a comment.

**Incident intake:** the REST API with a service account (what DummyCommerce uses), the
console by hand, seeded demo data, or service-scoped log ingestion with automatic detection.

**Console:** incident register with severity and status, incident detail with activity
timeline and comments, and the investigation view showing the five agent route with real
durations, reasoning, and the final report.

**Demo data:** `scripts/seed_demo.py` seeds three users, six incidents across every
severity and status, comments and timelines, then replays two *real* captured
investigations from `scripts/demo_fixtures.json`. The fixtures were produced by
`scripts/capture_fixtures.py` running live against real DummyCommerce logs, so a deployed
demo shows genuine agent output with no log file and no API call.

**Deployment:** Dockerfiles for the API and DummyCommerce, a compose stack with PostgreSQL,
Redis, Jaeger, API, worker, and DummyCommerce, a persistent log volume, migrations at container
start, `$PORT` injection for managed platforms, and a boot-time validator that refuses a
placeholder JWT signing key.

**Integrations and access control:** users have `admin`, `responder`, or `viewer` access.
Registration always creates a responder; an administrator assigns roles at
`PATCH /auth/users/{id}/role`. The demo seed makes `demo@mango.dev` an administrator, and
`python -m scripts.set_user_role <email> admin` bootstraps an initial administrator. Slack
incoming webhooks receive incident-opened, investigation-completed, and escalation notices
when `SLACK_WEBHOOK_URL` is configured. Admin-managed escalation policies can reassign
unacknowledged incidents after their configured delay; Celery Beat checks them once a minute.

**Evaluation tooling:** `backend/evals/` contains 50 reproducible synthetic scenarios
(10 DummyCommerce fault families × 5 evidence/noise variants), an existing-pipeline runner,
answer-blind category/service extraction with exact-match scoring, a separate root-cause
judge, and confidence calibration. Every model call uses the existing quota guard. Atomic
checkpoints resume completed nodes and grades without paying for them again. Run
`python -m evals.run --report` from `backend/`; measured coverage and results are recorded
in `backend/evals/RESULTS.md`. On 22 October 2026 (India time), the Gemini run graded 2/50
cases: category 2/2, service 1/2, and root-cause agreement 2/2. An OpenRouter partial
baseline is preserved separately in `backend/evals/openrouter-baseline/RESULTS.md`; it
graded the same 2/50 cases at category 2/2, service 1/2, and agreement 2/2. Both subsets
are correlated and too small to claim benchmark accuracy. The OpenRouter run's probe budget
recorded 19/20 requests used, including two provider-rejected calls; 48 cases and the
ten-case human review remain pending.

**Observability:** FastAPI request traces propagate through Celery into worker spans for each
agent node and export to Jaeger. `/metrics` exposes request and investigation duration,
provider calls, daily budget remaining, queue depth, ingested records, and detection firings.
`load/ingest.js`, `load/api.js`, and `load/investigation.js` exercise the main load paths. The
live k6 measurements remain pending because k6 is not installed in this environment.

**Tests:** 238 backend tests pass against in-memory SQLite with `StaticPool`; Ruff passes. The
DummyCommerce suite was not runnable here because its environment has no pytest installed.
The prior count of 214 (199 backend + 15 DummyCommerce) is stale. Backend tests also verify
the new ingestion behavior. CI runs both suites.
(E, F, I, UP, B; line length 100). Both run in CI on every push.

### Known limits of the current build

- Phase 4 is implemented. One full API investigation ran through Celery/Redis and PostgreSQL,
  including one ingested evidence record; the eight-run/four-worker acceptance measurement
  remains pending.
- Log ingestion and rule-based detection are implemented in Phase 1. The live 10k replay
  passed; the 500-record p95 acceptance measurement remains pending.
- Phase 5 tooling exists, but the full 50-case live baseline and manual judge check remain.
  A cold evaluation costs 250 logical calls, including extraction and judging; the 20/day
  guard remains in force. No full-benchmark accuracy or retrieval lift can yet be claimed.
- Phase 7 behavior is implemented and tested locally; Slack delivery and scheduled escalation
  still need configured integration credentials and a live Compose run.

## 4. What is left

Seven phases, in `plan.md` with acceptance criteria and the command that measures each.
Summarised:

| Phase | What | Why it matters |
|---|---|---|
| 1 | **Implemented; acceptance measurement pending.** `POST /ingest/logs`, indexed `log_records`, scoped service keys, rule-based incident detection, and database-backed evidence retrieval are built and tested. The live p95 measurement still needs to run. | Mango *finds* failures instead of being told about them. |
| 2 | **Implemented and measured.** The live API/PostgreSQL replay produced 400 failures → 6 incidents (66.7:1). The replay command tags each run and waits for all ingestion and detection work before measuring. | Measure how many repeated failures collapse into incidents. |
| 3 | **pgvector RAG over history.** Embeddings of resolved incidents, HNSW index, a new `history` graph node feeding prior diagnoses into the root cause prompt above a similarity floor. | The agents reason from everything already learned, not one incident's logs. |
| 4 | **Implemented; multi-worker acceptance measurement pending.** Celery/Redis workers, two retries per graph node, resume from persisted node outputs, SSE in the console, PostgreSQL atomic daily budget, and shared Redis request pacing are built and tested. The eight-run/four-worker measurement still needs PostgreSQL and Redis running. | Removes the in-process queue and per-process budget limit. |
| 5 | **Complete the live baseline and human review.** The 50-scenario harness, grading, caching and calibration tooling are built (section 3). Run all cases under the existing quota, then independently check ten judge decisions. | Record real accuracy and calibration before changing retrieval. Partial runs are labelled, not extrapolated. |
| 6 | **Implemented; live load measurement pending.** OpenTelemetry request-to-Celery-to-agent traces, Prometheus metrics, and k6 scripts for ingestion, register reads, and investigation submission are built. Docker/k6 acceptance run remains pending. | p95 and throughput measured rather than asserted. |
| 7 | **Implemented; live integration run pending.** Slack incoming webhooks, minute-based escalation policies, incident acknowledgement, and `admin` / `responder` / `viewer` RBAC are implemented. Slack delivery requires `SLACK_WEBHOOK_URL`; the live Compose scheduler verification remains pending. | Reads as an on-call tool, not a ticket tracker. |

**Build order:** 5 (baseline) → 1 → 2 → 3 → re-run 5 for the lift → 4 → 6 → 7.

**One rule for whoever implements this:** throughput, latency and the collapse ratio are
reproducible from a command in this repo. Accuracy is the only figure an interviewer can
test by asking what the evaluation set was. Measure it, never invent it.
